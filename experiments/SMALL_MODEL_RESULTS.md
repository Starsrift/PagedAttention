执行日期：2026-10-23，开始时间 08:24（Asia/Shanghai）。
方案：[SMALL_MODEL_PLAN.md](SMALL_MODEL_PLAN.md)。总体结果：**E1–E5 全部通过**。

## 一、本次回答了什么问题

本机已经成功加载真实小模型，并让分页缓存实际参与了模型的 Prefill 和逐 token Decode。
本轮受控实验中，分页缓存与 Transformers DynamicCache 的逐步 logits 和生成 token 保持一致。
真实多层、多 KV 头的前缀共享、写时复制和回收也得到验证。

当前实现仍在 attention 之前重建连续 K/V，验证的是分页存储和生命周期适配的正确性。
本轮教学适配器没有表现出速度或单请求内存优势，不能据此宣称完成了原生分页 Kernel 或 vLLM 性能复现。

## 三、实验目标、步骤及评测结果

| 编号 | 目标与主要步骤 | 通过标准 | 实测结果 |
|---|---|---|---|
| E1 | 加载 FP16 模型，执行三个固定提示词的普通生成 | 无异常、logits 有限，至少生成一个 token | 3/3，通过 |
| E2 | 取得真实 K/V，按 B=4/16/32 写入池并读回 | 各层 K/V 形状、dtype、内容完全相同，块数与尾空满足公式 | 15/15，通过，每例检查 28 层 |
| E2 错误对照 | 在 T>B 时故意交换两个块表项，随后恢复 | 检出错误，恢复后读回完全一致 | 6/6 检出并恢复 |
| E3 | 使用 Cache 接口，将分页存储直接接入模型逐步推理 | logits 满足固定容差，贪心 token 完全相同 | 9/9，通过，共 183 次逐步 logits 对照，最大绝对差值 0 |
| E4 | 按 B−1/B/B+1 前缀长度 fork 两个分支，分别追加不同 token | 分支结果符合参考、父缓存和另一分支不变、引用正确、全部回收 | 9/9，通过，18 个分支输出的 logits 差值均为 0 |
| E4 池耗尽 | 每层仅保留一个已使用的块，共享尾块写入时强制分配失败 | 长度、块表、引用计数、空闲列表和原 K/V 不变 | 28/28 层通过，释放后全部回收 |
| E5 | 64 token 输入、8 次单 token Decode，预热并重复测量 | 保留完整样本，空间核算与分配对象一致，不预设性能提升 | 两种方法各 3 次正式重复完成，数据见下表 |

E3 使用的事前容差是 `abs(error) <= 0.02 + 0.002 * abs(reference)`。
实际误差为 0 是本轮相同模型、相同 eager 后端、短上下文条件下的观测，不保证更换后端、精度或输入后仍然逐位相同。
183 次对照包含每个案例的 prefill 预测及后续 decode 预测，不应将其全部称为 decode 步数。

### E1 的实际生成样例

- 输入：`用一句话解释什么是键值缓存。`
  输出：`键值缓存是一种用于存储数据的机制，以提高数据访问效率和系统性能。`
- 输入：`What is the capital of France? Answer briefly.`
  输出：`The capital of France is Paris.`
- 输入：`请列出学习编程的两个建议。`
  输出以 `学习编程的两个建议如下：1. **持续学习与实践**` 开始，在 32 个新 token 处截断。

三个输入经 chat template 处理后分别为 21/22/20 token，生成分别为 21/8/32 token，前两项包含末尾 EOS。
这些样例只证明生成路径可执行，不构成回答质量评测。

### E4 的共享与 CoW 证据

每种块大小分别检查 B−1、B、B+1 三种前缀长度。父缓存保留，两个分支各追加一个不同 token。

- 未满的共享尾块：每个分支在每层复制一次尾块，两分支合计 56 次真实张量复制。
- 刚好填满的前缀：保留共享完整块，两分支分别领取新块，CoW 次数为 0。
- 每次操作后按所有活动块表重新计算引用计数，与池内记录逐项比较。
- 分支写入后，将父缓存、未写分支和已写另一分支与冻结快照比较，并将分支全部 K/V 与各自独立 DynamicCache 比较。
- 全部关闭后所有物理块回到空闲列表。

逻辑 OOM 测试直接针对每层缓存的共享尾块分配失败。它没有证明整个多层模型 forward 在任意失败时具有事务原子性，也没有故意耗尽显卡显存。

## 四、耗时与显存观察

条件：输入 64 token，8 次单 token decode，B=16。每种方法先预热一次，正式各重复 3 次，交替运行顺序，GPU 同步后计时。
下表 prefill 为 3 次正式样本的中位数，decode 为“各轮 8 步耗时中位数”的中位数。分配数据在三次正式运行中相同。

| 指标 | DynamicCache | 教学分页适配器 |
|---|---:|---:|
| Prefill 中位数，ms | 51.070 | 61.004 |
| 单步 Decode 中位数，ms | 46.644 | 54.508 |
| 最终活跃分配增量，MiB | 7.87549 | 15.75049 |
| 峰值新增活跃分配，MiB | 8.89160 | 17.79004 |
| 最终缓存长度 | 72 token | 72 token |

这些都是相对当轮基线的 PyTorch `memory_allocated` 数据，基线已经包含常驻模型等对象。
不是整卡显存占用，也不是 CUDA reserved 缓存。额外约 512 bytes 包含仍存活的单 token 张量和分配粒度影响。

### 真实模型的空间核算

每 token、全部 28 层的 K/V 字节数为：

`2 × 28 × 8 × 128 × 2 = 114688 bytes = 112 KiB`

- 有效 72 token 的 K/V 为 `72 × 112 KiB = 7.875 MiB`。
- B=16 时使用 5 个逻辑块，每层占用 80 个槽位，对应 `8.75 MiB` 的已映射块容量。
- 本实验为每层预分配 9 块，共 144 个槽位，对应整个池 `15.75 MiB`。
- 已映射块尾空为 8 个槽位，共 `0.875 MiB`。池内另外 64 个尚未映射的槽位为 `7 MiB`。
- 因此“有效 K/V”“已映射块”“整个预分配池”和“临时重建张量”需要分别报告。

单请求连续 DynamicCache 没有为每条序列预留 512 槽，因此不能套用此前合成静态基线的节省比例。
本轮池容量有额外余量，且分页读回会创建临时连续张量，故当前实现的活跃分配与耗时都高于连续缓存。
结果不能用来判断原生分页 Kernel 或大规模并发场景的收益。

实验开始时 GPU 利用率采样为 8%，结束采样为 14%，桌面活动未隔离。
这里只保留小样本的本机教学观察，没有计算服务端吞吐、TTFT、TPOT 或稳定尾延迟。
